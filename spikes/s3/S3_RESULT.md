# S3_RESULT.md — multi-file patch atomicity

Host: Darwin 25.6.0 (arm64), Python 3.12.14 (`host.json`).

Status: **evidence-gathering spike; its recommendation has since been
accepted as ADR 0003** (`docs/adr/0003-recover-partial-patches-by-replacing-worktree.md`,
Accepted). No production code under `src/codeagent` was read,
imported, or modified for this spike, and no existing test under
`tests/` was touched. `spike_s3.py` implements its own throwaway,
minimal multi-op "apply" function purely to have something to apply —
the real `codeagent.patch.GitPatchApplier` is deliberately
single-operation only (Milestone 1 slice B's explicit scope) and
cannot express a multi-file proposal at all, so there was nothing
existing to exercise. This answered a design question for a
not-yet-built Milestone 2 component; it does not validate anything
currently shipped, and no B2+C implementation exists yet.

This document reflects the **retained run** whose raw JSON lives
alongside it (`result1.json`, `result2.json`, `result3.json`,
`summary.json`, `host.json`, `baseline-worktrees.txt`,
`final-worktrees.txt`, `run.log`). The script was run more than once
during development of the harness itself, but only one run's evidence
is retained and referenced here — this document makes no claim about
cross-run repetition or its stability; every observation below cites
the exact values in the retained JSON.

## Setup

Three independent experiments, each against its own fresh, disposable
scratch Git repository + worktree created under a unique
`tempfile.mkdtemp(prefix="codeagent-spike-s3-")` root — never a fixed,
recursively-deleted `/tmp` path, and never the CodeAgent checkout. Each
scratch repo starts with three committed files (`a.py`, `b.py`,
`c.py`), each containing one distinctive original string
(`A_ORIGINAL`/`B_ORIGINAL`/`C_ORIGINAL`). A "proposal" is a list of
`PatchOp(relative_path, expected_text, new_text)` — replace exactly one
occurrence of `expected_text`, same shape as the real
`GitPatchApplier`'s single operation, just allowing more than one in a
list.

`validate_op`/`validate_all` are read-only: they check each target file
exists and that `expected_text` occurs in it exactly once (0 = not
found, >1 = ambiguous), and never write anything regardless of
outcome. `apply_one` is the deliberately naive approach under test:
read, do the replacement, `open(..., "w")`, `flush()`, `os.fsync()` —
no write-to-scratch-then-atomic-rename, no per-op commit. A
`manifest()` of a worktree captures `git rev-parse HEAD`, `git status
--porcelain`, and each of the three files' existence/size/sha256 —
equality of two manifests is the evidence for "byte-for-byte
unchanged."

**Every infrastructure subprocess call fails loudly by default**
(`run(argv, check=True)` — the default; a nonzero exit raises
`CalledProcessError` immediately). This closes a real gap in the first
version of this harness: `git_head()`/`git_status()` previously
returned whatever `stdout` a failed git command produced (typically
empty), which a caller could misread as legitimate state rather than
"the command didn't run." The one deliberate exception is experiment
2's rollback command itself (`git checkout --`, called with
`check=False`) — whether that specific command succeeds or fails is
the thing experiment 2 measures, so it must not raise on the
experiment's behalf. `test_spike_s3.py` (15 tests) exercises this
directly: `test_git_head_raises_rather_than_returning_empty_string`
and its siblings prove the fix, using specific exception types
(`ValidationError`, `subprocess.CalledProcessError`) rather than bare
`Exception`.

Full command transcript: `run.log`, generated by the script itself as
it runs (a `log()` wrapper tees every line it prints into the file it
writes at the end) — a rerun does not require copying anything out of
a temp directory by hand. The unique scratch root is removed
unconditionally in a `finally` block; `summary.json["scratch_root_removed"]`
records the verified result of checking `not scratch_root.exists()`
afterward, and the script raises `AssertionError` if that check ever
fails.

## Experiment 1 — prevalidation atomicity

**Setup**: a 3-op proposal on a fresh worktree; op 3 targets `c.py`
with `expected_text` that does not appear anywhere in the file (a
validation-detectable mismatch). `validate_all` runs first; nothing is
applied unless it returns zero errors.

**Observation** (`result1.json`): `validate_all` reported exactly one
error (`c.py: expected_text not found`); no op was applied
(`rejected_before_any_write: true`); `manifest_before ==
manifest_after` exactly — same HEAD
(`ed9fe63055f62a7948f7316f332ca69b9be4f0f1`), same empty git status,
same size and sha256 for all three files.

**Classification: PASS — genuine prevalidation atomicity.** A proposal
containing any validation-detectable error never touches the
filesystem at all. This is the cheap, reliable guarantee the
hypothesis predicted.

## Experiment 2 — handled mid-application failure + rollback

**Setup**: a fresh worktree, a fully valid 3-op proposal. Op 1
(`a.py`) is applied for real. Before op 2 starts, a deterministic
`InjectedFailure` is raised and caught (standing in for a real
mid-application error — e.g. a disk-full condition, a second
validation surprise only detectable at write time). The harness then
runs one explicit rollback strategy: `git checkout -- a.py`.

**Observation** (`result2.json`):
- Before rollback ran, the mid-state manifest already differed from
  `manifest_before` (`intermediate_state_was_inconsistent: true`):
  `a.py`'s size changed from 33 to 32 bytes and its sha256 changed,
  `git status` showed `M a.py`, while `b.py`/`c.py` were untouched and
  HEAD had not moved. **A real, observable inconsistent state existed**
  for the entire window between op 1's write and the rollback command
  running.
- The rollback command (`git checkout -- a.py`, run with `check=False`
  since its outcome is the measurement) exited 0
  (`rollback_command_succeeded: true`), and the resulting manifest was
  exactly equal to `manifest_before` — same HEAD, empty status, and
  byte-identical `a.py` (`fully_restored_to_pre_apply_state: true`).

**Classification: rollback restored state for this case — this is
handled-failure recovery, not atomicity.** The distinction matters:
atomicity means the inconsistent intermediate state is never durably
observable in the first place. Here it *was* observable — any process
that inspected the worktree during the window between op 1's write and
the rollback call (a crash, a concurrent reader, the process being
killed one instruction earlier) would have seen `a.py` patched while
`b.py`/`c.py` were not, with no corresponding commit. The rollback
worked in this run because (a) only a tracked, previously-clean file
was touched, so `git checkout --` had something correct to restore
from, and (b) the rollback code itself ran to completion. Neither is
guaranteed in general — a *new* file created by an op has no HEAD
version to check out to (untested here), and rollback code that itself
fails partway (disk full, killed) is exactly experiment 3's scenario.

## Experiment 3 — interruption (SIGKILL) detection

Deliberately **not** called "crash consistency" in this revision: that
name implies a guarantee about the *data itself* surviving correctly
(the original S3 plan's own wording distinguishes this from
atomicity). What this experiment actually shows is narrower —
whether an interrupted apply leaves *evidence that it was
interrupted*, not that anything about the outcome is safe or complete.

**Setup**: a fresh worktree, the same fully valid 3-op proposal,
applied in a **child process**. The child applies op 1, `fsync`s it,
writes and `fsync`s a marker file, then spins forever
(`while True: time.sleep(0.05)`) with no further work scheduled and no
signal handler, `atexit` hook, or `finally` block registered to run
anything. The parent polls for the marker file (deterministic barrier:
op 1's write is guaranteed complete and flushed once the marker
exists), then sends `SIGKILL` the instant it appears.

**Observation** (`result3.json`): `child_returncode: -9`
(`child_killed_by_sigkill: true`, confirming a real, uncatchable kill —
**SIGKILL cannot run cleanup code**, so none was expected or
attempted; if a future implementation is added, it must not assume any
in-process cleanup runs on a hard kill). After the kill:
`a_py_patch_applied: true`, `b_py_patch_applied: false`,
`c_py_patch_applied: false`, `b_py_untouched`/`c_py_untouched: true`,
`head_unchanged: true`, `working_tree_dirty: true`.

**Classification: `partial_but_detectably_incomplete`.** The worktree
is neither fully original nor fully applied: exactly one of three
files is patched, the other two are byte-identical to their originals,
and no commit was ever made. Per the plan's pass criterion, this is a
**pass** — but the detectability is entirely a *convention*, not a
structural guarantee: it relies on whatever inspects the worktree
afterward knowing the rule "a completed apply always ends with a new
commit and a clean tree; anything else means an apply was
interrupted." Nothing in this naive implementation writes an explicit
transaction marker, lock file, or scratch-then-rename swap — if a
future version ever committed per-file instead of once at the end, or
if a caller failed to check for a dirty tree / stale HEAD before
trusting the worktree, this exact partial state would become
indistinguishable from "the plan intentionally only touched one file."
**This experiment establishes detection-and-rejection is possible, not
that the underlying data is handled with any crash-consistency
guarantee** — the two are genuinely different claims, and only the
first is supported by this evidence.

## Cross-experiment distinction (explicit, since this is the point of S3)

| | What was tested | What the evidence shows |
|---|---|---|
| Prevalidation atomicity | Rejecting a bad proposal before any write | **Real** — nothing is ever written if validation finds an error |
| Rollback after handled failure | Recovering after a *caught* exception mid-apply | **Recovery, not atomicity** — an inconsistent state was genuinely observable before rollback ran; rollback happened to succeed here but is a separate, fallible corrective step |
| Interruption detection | Recognizing (not surviving) an *uncaught, uncatchable* kill mid-apply | **Detectable by convention only** — no structural safeguard (no lock file, no atomic rename, no transaction marker) backs the detection; it works today only because completion is defined as "HEAD advanced + clean tree". Not a crash-consistency or data-safety guarantee. |

## Limitations of this spike

- Only one crash point was tested (immediately after op 1, before op
  2) — not a crash mid-write of a single file, not a crash after `git
  add` but before `commit`, not a crash during the rollback command
  itself. The instructions specifically asked for a barrier *after*
  the first write, not mid-write, so single-file write atomicity was
  never in scope here.
- Experiment 2's rollback strategy (`git checkout --`) was only
  exercised against a previously-tracked, previously-clean file. A
  proposal that creates a new file, or touches a file that already had
  uncommitted changes before the apply started, was not tested and
  would very plausibly behave differently (git has nothing to check
  out *to* for an untracked new file). **File creation, deletion,
  rename, and rollback-command failure itself are all untested and
  require dedicated Milestone 2 validation before any rollback
  strategy is trusted for arbitrary proposals.**
- Only 3 files and a single crash trial were run; no repeated/fuzzed
  trials to look for nondeterministic OS-level write-buffering
  behavior (the file sizes here are trivially small — 32-33 bytes — so
  `write()` completing atomically at the syscall level is unsurprising
  and may not generalize to much larger files).
- `os.fsync()` (not macOS's `F_FULLFSYNC`) was used — sufficient to
  prove the *process's own buffers* were flushed to the OS before the
  marker was written (which is what makes the SIGKILL timing
  deterministic), but not a claim about durability across a real power
  loss.
- Run once on macOS/arm64 in this session; the earlier draft of this
  document referenced a second re-run of the harness that is not
  retained as separate evidence — that claim has been removed, and
  only the single retained run above is cited. No Linux/x86_64 run was
  performed for S3.

## Decision table: what should v1 actually require?

| Option | What it guarantees | Cost | Recommendation |
|---|---|---|---|
| **A. Prevalidate only, no rollback, no interruption handling** (experiment 1's guarantee, nothing else) | Rejects known-bad proposals before writing. Silent on handled-failure or interrupted partial state. | Lowest — already what exists conceptually in `GitPatchApplier`'s single-op validate-then-write. | Insufficient alone for a true multi-file engine: a handled failure or interruption would leave an undocumented, silently-partial worktree. |
| **B1. Prevalidate + in-place rollback via `git checkout --`** (experiment 2's approach) | Adds recovery from *caught* exceptions mid-apply, restoring pre-apply state for tracked/clean files, by reverting them in place. Says nothing about untracked new files or a failing rollback command itself. | Moderate — one `git checkout --`/`git clean` call per touched-so-far file, wrapped in a try/except around the apply loop. | A viable minimum, but only once new-file and rollback-failure paths are validated (untested here — see Limitations). |
| **B2. Prevalidate + abandon-and-recreate**: on any mid-apply failure, discard the entire disposable worktree and recreate a fresh one from the last accepted checkpoint, rather than reverting individual files in place | Same practical outcome as B1 for the common case, but sidesteps B1's untested edge cases entirely (new files, partially-reverted state, a `git checkout` that itself fails) by never trying to reconcile a partially-mutated worktree at all — the whole disposable worktree is simply thrown away. | Similar or lower implementation cost than B1 (worktree create/remove is already a primitive `codeagent.workspace.GitWorktree` has), but relies on worktree create/delete themselves being reliable, which this spike did not stress-test. | **Potentially safer than B1 and worth preferring**, specifically because it has fewer distinct failure modes to reason about — but this preference is not yet backed by evidence; B2's own create/delete/rename behavior under failure is exactly as untested as B1's rollback command, and needs the same Milestone 2 validation before either is trusted. |
| **C. B1 or B2 + a documented, checked interruption-detection convention** (experiment 3's approach: commit-as-completion-marker) | Adds "if the tree is dirty and HEAD hasn't moved, the last apply was interrupted" as an explicit, documented invariant a caller (RunController) must check before trusting a worktree. This is **interruption detection/rejection**, not crash consistency — it says nothing about whether the partially-written data is safe, only that it can be recognized as incomplete and refused. | Low incremental cost on top of B1/B2 — the commit-last ordering already exists; the only addition is a documented check + a place in the controller that runs it (e.g. before trusting a worktree it's resuming). | **Recommended for v1 alongside whichever of B1/B2 is chosen.** Cheap, and turns today's incidental detectability into an intentional, checked invariant rather than a lucky accident. |
| **D. True crash consistency via write-to-scratch-then-atomic-rename per file, single all-or-nothing commit** | Would make experiment 3's classification `fully_original` or `fully_applied` unconditionally, not merely "detectable." This is the only option that would actually justify the name "crash consistency." | High — real design and implementation work: scratch file management, `os.replace` per file, careful ordering, its own new failure modes (disk space for duplicated content, directory-level rename semantics). Explicitly the kind of "larger redesign" this spike was told not to attempt. | **Defer to Milestone 2.** Not justified for v1's scope unless the product decision is that CodeAgent must survive an adversarial or flaky host process being killed mid-patch — a real but separate question from ordinary handled-failure recovery. |

**Decision (author-accepted): v1 requires B2 + C.** See
`docs/adr/0003-recover-partial-patches-by-replacing-worktree.md`
(Accepted) for the full recorded decision, consequences, and rejected
alternatives. In summary: on a handled mid-application failure, the
disposable worktree is discarded and recreated from the last accepted
checkpoint (B2) rather than reverted file-by-file (B1); before
trusting or resuming any worktree, the controller must check HEAD
equals the expected checkpoint and the tree/index are clean (C) — a
dirty tree or unexpected HEAD is treated as interrupted and never
resumed. **True crash consistency (D) is explicitly not guaranteed in
v1** — the claim is recovery plus interruption detection/rejection at
the controller boundary, not all-or-nothing filesystem visibility
during the write window itself. Per the ADR: B2's own create/delete/
rename behavior under failure, and what happens when disposal or
recreation itself fails, are **not** evidenced by this spike and are
required Milestone 2 failure-path testing obligations before any of
this is implemented.

This decision is recorded as ADR 0003; no implementation of B2+C has
occurred as part of this spike or its writeup.

## Cleanup evidence

`baseline-worktrees.txt` and `final-worktrees.txt` are identical (only
the scratch repo's own main worktree listed in both, confirmed via
`git worktree list` before the scratch root is ever deleted);
`summary.json`'s `no_leftover_worktrees_before_scratch_root_removal:
true` and `leftover_worktree_dirs: []` confirm this programmatically.
Separately and unconditionally, the entire unique scratch root
(`tempfile.mkdtemp` output, recorded in `summary.json["scratch_root"]`)
is removed in a `finally` block after every run, and its removal is
independently verified afterward via `Path.exists()` —
`summary.json["scratch_root_removed"]: true` for the retained run,
and the script itself raises `AssertionError` (failing loudly, not
silently) if that check ever comes back false.
